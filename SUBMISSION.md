# NammaMart data pipelines — Mohammed Imtiyaz

FDAIE Module 2 · Cohort 4 · Insight Global · revised 21 October 2026

## Executive result and reproduction

My starting question was whether NammaMart could give leadership a trustworthy morning sales number while still explaining corrections and rejected records to Finance. I implemented the same six-file exercise in two ways so I could compare the answers, not just the code structure. My recommendation below is based on these local runs; I have not operated either design as a production service.

I built both requested pipelines on the unmodified six-file class dataset. The ETL cleans with pandas before loading `etl_*` tables; the ELT appends every source row to `raw_*` and transforms in DuckDB SQL to `stg_*` and `mart_*`. The five source extracts are parallel Airflow tasks. Both DAGs imported without errors and completed successful local Airflow test runs on 12 October 2026. The 20 isolated scenario tests (ten scenarios × two pipelines) passed again on **21 October** with a fixed 12 October validation clock. I also ran missing-file failure and Airflow UI Clear recovery on both DAGs. These are dated local results, not a production SLA claim.

In the **12 October evidence snapshot**, after the supplied increment, both accepted fact sets contained **2,021 rows and ₹991,180.80 net revenue**. The baseline before the increment was **1,896 rows and ₹930,779.95**. Repeating the load did not change accepted fact counts or sums in that snapshot. The SQL and actual result CSVs for all six questions from **both** pipelines are in [QUERY_RESULTS.md](evidence/results/QUERY_RESULTS.md). Answers 1–5 match row-for-row. Answer 6 has the same 30 file/rule groups but three count differences: ETL retains historical source-rule failures for base orders `ORD000017` and `ORD000332` (`known_store_id`) and `ORD000822` (`known_product_id`), while ELT's current-state staging no longer flags them after valid correction rows arrived in the increment. Thus ETL counts 315 vs ELT 313 for base `known_store_id`, and 132 vs 131 for base `known_product_id`. The business meaning of “rejected today” needs a client choice: newly rejected input events or currently invalid order keys. The [run audit](evidence/results/pipeline_runs.csv), [quality scorecard](evidence/results/dq_results.csv), [reconciliation](evidence/results/payment_reconciliation.csv), and [quality trend](evidence/dq_trend.svg) are exported from the local warehouse. These exports exclude names, email addresses, and phone numbers. The local warehouse and row-level quarantine are intentionally not committed because they contain source-derived data.

**21 October repeatability check.** An initial rerun passed 14 of 20 tests; six fixed-count assertions changed as the calendar advanced. Two source orders are stamped `2026-10-21 10:15:00`, so a real-time future-order rule changes eligibility. I made the validation clock injectable and reran all **20 tests successfully** with an explicit `2026-10-12 12:00:00` as-of time ([recorded output](evidence/test_run_2026-10-21.md)). The DAGs still use the actual run time by default. This verifies the dated test expectations without editing the six source files. The 12 October revenue and reconciliation exports remain historical snapshots, not a claim that a live 21 October run has identical totals.

Reproduce: start Docker, run `astro dev start`, run `astro dev run dags list-import-errors`, then `astro dev run dags test nammamart_etl_imtiyaz 2026-10-12` and the matching `nammamart_elt_imtiyaz` command. The incremental path is selected by DAG run config `{"incremental": true}`; the isolated test suite uses `.venv/bin/python -m pytest -q tests/test_nammamart_assignment.py`. Export business results with `.venv/bin/python -m include.export_nammamart_evidence`. Local Astro exposes Airflow at `http://nammamart-pipeline.localhost:6563`; this is not a public link.

Questions for NammaMart: (1) Should cash-on-delivery orders without a gateway `SUCCESS` payment be considered unreconciled at the morning cutoff? (2) When a delivered order is returned later, should finance restate the historical order date or show a separate return-date adjustment? (3) Is a zero store capacity a closure signal or a malformed master record, and who can approve its correction?

## Part C — schedule and SLA

Both DAGs use `0 9 * * 1-6`, explicit `Asia/Kolkata` start dates, `catchup=False`, two one-minute extraction retries, a 15-minute task timeout, and `max_active_runs=1`. The final audit task has zero retries so a failed run is marked failed promptly after extraction retries. Both DAGs are enabled in the local Airflow UI; on 12 October the UI displayed **13 October 2026, 09:00 IST** as the next run for each. **09:00 IST is 03:30 UTC**. A UTC start date with a 09:00 cron would instead schedule **14:30 IST**, five and a half hours late. `catchup=False` avoids replaying every missed historic day during local development. If the laptop or Docker is off at 09:00, the local scheduler cannot execute the run; once restored, operational recovery and a manual trigger must be checked. No uptime or before-09:00 delivery is claimed.

**Observed 13 October scheduled run:** Airflow recorded a 09:00 IST scheduled time for each DAG, but both actually started at **09:46:17 IST** and finished at **09:46:42 IST**. Both states were `success`; the accepted facts remained **2,021 rows and ₹991,180.80** in each pipeline. The ETL audit recorded 5,372 extracted rows and the ELT audit 5,212: ETL reprocessed the supplied correction file while ELT retained its earlier append-only raw correction rows, so the accepted fact totals still reconciled. The macOS power log shows the laptop in deep idle with a dark wake at 09:46:12 IST, which is consistent with the local scheduler being unavailable at the 09:00 cutoff; it does not prove a production infrastructure issue. This run **missed the requested timing SLA** despite finishing successfully. An always-on deployment and a start time earlier than the agreed reporting cutoff are required before claiming an on-time service.

The brief contains conflicting wording: “ready before 9:00” but specifically mandates a **9:00 start** and later describes a 9:30 stand-up. A 9:00 start cannot guarantee data ready before 9:00. I used the required 9:00 schedule; production sign-off needs an agreed cutoff (for example before 9:30) or an earlier trigger based on measured runtime.

## Part D — quality scorecard

Both paths check completeness (required keys/category/minutes), uniqueness (business keys), validity (allowed status/mode and parseable dates), accuracy (positive quantity/prices, formula, duration), consistency (foreign keys and payments), and timeliness (future dates and stale latest order). Critical failures are kept out of reporting facts and written with reasons to quarantine; warnings are logged but do not necessarily block a row. `dq_results` records `run_id`, `dag_id`, check, dimension, severity, rows checked/failed, status, and timestamp each run. The ETL uses Python rules; the ELT uses SQL staging and quality statements. The bonus `mart_store_capacity` flags store-day volumes against `capacity_orders_per_day`; [trend chart](evidence/dq_trend.svg) reads the scorecard.

## Part E — governance

**Ownership and rule change.** Ops owns orders/stores, Finance owns payments and reconciliation policy, CRM owns customers, merchandising owns products, and the FDE/data owner operates warehouse outputs. A rule change such as a 120-minute maximum requires Ops and Finance approval, a documented version/date, impact estimate, and a rerun before the KPI changes.

**Data dictionary.** This is the business-level dictionary for the accepted fact and ETL dimensions (the ELT equivalents are `mart_fact_orders` and the `stg_*` tables). Numeric types below describe the intended value; the ETL pandas loader can infer a wider DuckDB numeric type, while ELT SQL uses `DOUBLE` for several numbers. I would pin these to `DECIMAL` for money and `INTEGER` for counts in a production contract. “Linkable” means an ID is not a name but can identify a person when joined to customer records. All permitted values apply **after** normalization and validation, not to raw CSV text.

The ELT staging tables also retain `_source_file`, `_source_row`, `_run_id` (text/integer lineage fields), `failure_reason`, `warning_reason` (text), and `dq_status` (`Passed`/`Critical`). They are operational metadata, not business facts; a failed staging row is excluded from the accepted mart. The ETL dimension/fact columns are selected in [the ETL loader](include/nammamart_etl.py); ELT casts and checks appear in [staging SQL](include/sql/01_staging.sql) and [mart SQL](include/sql/02_marts.sql).

**Lineage.** In `mart_daily_store_kpis`, S01 / North on 2026-09-01 has ₹1,410.80 net revenue. It traces to `orders.csv` row 1369 (`ORD000013`, ₹28.80), row 728 (`ORD000025`, ₹788), and row 444 (`ORD000058`, ₹594); 28.80+788+594=1,410.80. The ETL can trace using retained order IDs and source row issue logs; ELT is easier to replay because raw records retain source file, row lineage and run metadata. Row numbers here refer to data rows in the CSV, not line numbers including the header.

**Personal data and law.** Raw customers include `full_name`, `email`, `phone`, `city`, `area`, `pincode`; customer/order IDs and order history can also identify or profile a person when linked. `manager_name` is employee personal data. Reports omit raw names and mask email/phone, retaining partial values only for operational matching. The Indian [Digital Personal Data Protection Act, 2023](https://www.meity.gov.in/static/uploads/2024/02/Digital-Personal-Data-Protection-Act-2023.pdf) and [DPDP Rules, 2025](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf) are relevant; duties include lawful purpose/notice, safeguards, rights handling, and erasure when retention is no longer justified. [Commencement is phased](https://www.meity.gov.in/static/uploads/2025/11/c56ceae6c383460ca69577428d36828b.pdf), so this is a design obligation, not a claim that all provisions were in force on the submission date.

**Access control.** I would limit raw customers and row-level quarantine to named CRM stewards and incident responders, with time-limited engineer access. Analysts and executives would use masked marts; Finance would see reconciliation. Local DuckDB has no built-in role policy in this setup, so a production deployment needs governed storage, encryption and access logs.

**Retention.** My provisional policy is 90 days for raw and quarantine and 13 months for masked marts; Finance and legal owners must approve the actual periods and any statutory hold. Expiry means deleting working copies and ensuring backups age out, while honoring applicable correction and erasure requests. These durations are proposals, not implemented enforcement.

**Secrets.** I did not configure a Slack webhook or other external alert credential for this local build. In deployment I would keep credentials in Airflow Connections/Variables backed by a managed secret store, with least-privilege access; a DAG or GitHub commit is not a safe secret store.

**Audit and corrections.** For rejected `ORD000014`, ELT can show the exact `raw_orders` row and `elt_quarantine.failure_reason=unknown_store`; ETL records the original row in local CSV quarantine. Neither enters the accepted fact revenue total. A DELIVERED-to-RETURNED correction replaces the current status through an upsert, so September's current-state revenue is restated; Finance must approve this policy. To retain both “as originally reported” and “as currently known,” add versioned/snapshot facts and a return adjustment ledger. The current implementation retains ELT raw events but does **not** yet expose a historical as-of finance mart.

## Part G — recommendation to Sameer, CTO

Adopt **ELT as the system of record with a gated, finance-safe mart**, while retaining the ETL implementation as a comparison and fallback. In the dated 12 October snapshot, both approaches yielded the same accepted 2,021 facts and ₹991,180.80 after the increment. ELT additionally preserves all source rows, including invalid rows, and the correction history needed to investigate the finance/ops disagreement. Its SQL staging keeps bad records out of marts and its reconciliation exposed ₹103,372.70 of unmatched amount in that snapshot: ₹102,912.70 from missing successful payments plus ₹460 of amount mismatches. That number is an investigation queue, not proven lost revenue; cash-on-delivery timing and refund policy need Finance sign-off.

ELT makes new rules and replay easier because raw data remains available. ETL has a simpler pre-warehouse exclusion boundary but loses convenient raw replay unless the quarantine/source archive is separately governed. At 1,000× scale, a single-file local DuckDB and daily full staging rebuild are not sufficient; partitioned storage, incremental SQL models, concurrency controls, retention and access controls would need engineering and cost testing. On today's small open-source local workload, there is no credible basis to claim one is faster or cheaper in production.

Top three risks: (1) raw PII in ELT needs strict access/retention controls; (2) Finance semantics for COD, refunds and historical restatement remain undecided; (3) a laptop-hosted 9 AM DAG cannot guarantee the leadership SLA. I would sign off only after those policies are agreed, recovery is operationalized with alerting, and an always-on deployment meets a measured cutoff.
